# Aula 4: Estrutura de executáveis do Windows (PE)

## 1. A ideia em uma frase

> Até agora olhamos o arquivo como bytes. Agora vamos abri-lo pela **estrutura** e perguntar: o que este programa pretende FAZER?

PE = **Portable Executable**, o formato de todo `.exe`, `.dll`, `.sys` e `.scr` do Windows.

## 2. O mapa de um executável

```
  ┌───────────────────────────┐ 0x000
  │ "MZ"  cabeçalho DOS        │  (o mesmo magic byte da Aula 2!)
  │   ...e_lfanew ─────────────┼──┐  aponta onde o PE começa
  ├───────────────────────────┤  │
  │ "PE\0\0"                   │◄─┘
  │ cabeçalho COFF            │  máquina (x64?), nº de seções, data
  │ cabeçalho opcional        │  ponto de entrada, tabela de diretórios
  ├───────────────────────────┤
  │ tabela de seções          │  nome, tamanho e permissões de cada seção
  ├───────────────────────────┤
  │ .text   │ código executável          X-R
  │ .rdata  │ textos, constantes         --R
  │ .data   │ variáveis                  -WR
  │ .rsrc   │ ícones, imagens            --R
  │ .idata  │ tabela de IMPORTS ◄── o que o programa pede ao Windows
  └───────────────────────────┘
```

A biblioteca `pefile` lê tudo isso pra gente. O nosso trabalho é **interpretar**.

## 3. Não é "é vírus ou não": é somar indícios

Um executável legítimo pode ter um sinal estranho. Um malware costuma ter
vários. Por isso o motor dá **pontos** a cada sinal e soma:

```
    0 ─────────────── 3 ─────────────── 6 ──────────►
    ✅ normal         🟡 suspeito        🚨 malicioso
    (poucos pontos)   (alguns sinais)    (vários sinais juntos)
```

Isso se chama **detecção heurística baseada em pontuação**, e é como motores de
verdade combinam dezenas de regras fracas numa decisão.

## 4. O que o motor procura

### a) Imports: as "ferramentas" que o programa pega emprestado do Windows

Um programa não fala direto com o hardware: ele pede funções ao sistema. A lista
dessas funções (a tabela de imports) é quase uma **lista de intenções**.

```
  CreateFileW, ReadFile, printf ....... abrir e ler arquivos          (normal)
  socket, connect, send ............... usar a rede                   (normal)

  VirtualAllocEx ─┐
  WriteProcessMemory ├─ juntas = "a receita" de INJETAR código em      🚨 +4 pts
  CreateRemoteThread ┘  outro processo (técnica clássica de malware)

  SetWindowsHookExA ................... capturar teclas (keylogger)    🚨 +3 pts
  IsDebuggerPresent ................... "estou sendo analisado?"       🟡 +1 pt
```

> ⚠️ **Conhecer esses nomes é defesa.** São exatamente as funções que um analista
> de segurança procura ao examinar um executável suspeito. Saber o que o malware
> *usaria* é o que permite detectá-lo.

### b) Seções: a "planta" do executável

```
  nomes normais:  .text  .data  .rdata  .rsrc  .reloc  .idata  ...

  UPX0, UPX1  ────► sobraram de um empacotador (packer)               🟡 +3 pts
  .vmp0, .enigma1  ► ofuscadores comerciais usados por malware        🟡 +3 pts
  .evil, xptoo  ───► nome fora de qualquer padrão                     🟡 +1 pt
```

### c) Permissões contraditórias

```
  seção .text normal:  X - R   (executa e lê)
  seção suspeita:      X W R   (executa E pode se reescrever) ◄── código     🟡 +2 pts
                                que se modifica sozinho = típico de packer
```

### d) Código com entropia alta (puxando da Aula 3!)

Se a seção `.text` (o código) tem entropia ≥ 7.2, o código "de verdade" está
cifrado e só aparece quando o programa roda. Mais um elo com a aula anterior.

## 5. O raio-X na prática

```
  python -m superav pe C:\Windows\System32\notepad.exe

  seção        tam.(bytes)  entropia  flags (X=exec W=grava R=lê)
  .text           159,744     6.24  X-R   ◄── código, entropia normal
  .rdata           45,056     5.58  --R
  .data             4,096     1.62  -WR   ◄── dados, pode gravar mas não executa
  .rsrc           126,976     6.97  --R   ◄── ícones (entropia alta é normal aqui)
  .reloc            4,096     1.62  --R

  imports: 315 funções de 50 DLLs

  Veredito: ✅ passou  1 pts — indícios fracos: IsDebuggerPresent
```

O `notepad.exe` usa `IsDebuggerPresent` (1 ponto), mas isso sozinho é fraco e
ele passa. Exatamente o que queremos: **não assustar com um único sinal**.

## 6. 🔍 Aconteceu na aula: um falso positivo real

Meu teste dizia que `kernel32.dll` deveria passar limpo. Ele **falhou**:

```
  kernel32.dll  🟡 5 pts — injeção de código: CreateRemoteThread,
                VirtualAllocEx, WriteProcessMemory, ...
```

Por quê? Porque a `kernel32.dll` é **a própria biblioteca do Windows que
implementa essas funções**. Claro que ela as referencia! É um falso positivo
clássico:

```
  programa de usuário que CHAMA WriteProcessMemory ──► suspeito  ✅ faz sentido
  a DLL do Windows que OFERECE WriteProcessMemory  ──► suspeito  ❌ falso positivo
```

Como os antivírus de verdade resolvem isso? Com uma **allowlist**: arquivos
assinados digitalmente pela Microsoft recebem o benefício da dúvida. Guardei
isso como `test_falso_positivo_conhecido_kernel32` — reconhecer os próprios
limites faz parte de construir um detector honesto.

## 7. A grande vantagem sobre as aulas anteriores

```
  hash      ──► só pega o que JÁ viu
  magic     ──► pega o disfarce
  entropia  ──► pega o "empacotado"
  PE        ──► olha a INTENÇÃO: "este programa quer injetar código / espionar
                o teclado" — mesmo num malware totalmente novo, sem assinatura
```

É a heurística mais poderosa até aqui, e também a que mais exige cuidado com
falsos positivos.

## 8. Segurança e dependência nova

- Esta aula instala a primeira biblioteca externa: **`pefile`** (`pip install -r requirements.txt`).
  Ela só **lê** a estrutura; nunca executa o arquivo.
- Não criamos nenhum `.exe` de teste: a lógica de pontuação é testada passando
  listas de nomes direto para as funções (`avaliar_imports`, `avaliar_secoes`), e
  os testes que abrem arquivos de verdade usam os programas do próprio Windows.
- Se o `pefile` não estiver instalado, o motor fica ⏳ pendente em vez de quebrar.

## 9. Mão na massa

```powershell
.venv\Scripts\Activate.ps1
pip install -r requirements.txt

python -m superav pe C:\Windows\System32\notepad.exe
python -m superav pe C:\Windows\System32\calc.exe
python -m superav pe C:\Windows\System32\kernel32.dll     # veja o falso positivo

# um programa que você mesmo tenha instalado:
python -m superav pe "C:\Caminho\Para\AlgumPrograma.exe"
```

## 10. Exercícios

1. Rode `pe` em 3 programas do seu PC. Algum dispara algum ponto? Veja se faz sentido.
2. Por que a seção `.rsrc` (ícones) costuma ter entropia alta sem ser suspeita?
   (Dica: lembre da Aula 3 e pense no que tem dentro de um ícone.)
3. A função `avaliar_imports` só acusa injeção quando há **2 ou mais** funções do
   conjunto. Por que não bastaria 1? Abra `superav/motores/pe.py` e veja.
4. Pensando em falso positivo: um instalador legítimo (setup.exe) muitas vezes é
   "empacotado" e tem entropia alta. Como você evitaria acusá-lo? (Pense em
   assinatura digital, que é justamente a allowlist da seção 6.)
5. Desafio: adicione uma regra que marque +1 ponto quando o executável NÃO tem a
   seção `.rsrc` (sem ícone nem informação de versão), algo comum em malware
   "cru". Escreva o teste antes do código.
